**4.3 Core Technologies**

The development of this system leverages several powerful, open-source libraries and frameworks:

*   **OpenCV**: A fundamental library for computer vision tasks, used for image and video processing, face detection, and user interface elements.
*   **dlib**: A modern C++ toolkit with Python bindings, used for its high-quality face detection and facial landmark prediction capabilities, which are essential for liveness detection.
*   **DeepFace**: A comprehensive, lightweight face recognition framework that provides access to state-of-the-art models, including **Facenet**, which is used in this project for generating 128-dimensional facial embeddings.
*   **NumPy**: A critical library for numerical operations, used extensively for handling and manipulating facial embeddings.
*   **SQLite**: A self-contained, serverless SQL database engine used for storing all student data, including registration details, facial embeddings, and authentication logs.

**4.4 Database Schema**

The system's data is stored in a SQLite database (`students.db`) with a well-defined schema designed for efficiency and integrity.

[--- INSERT SCREENSHOT HERE: A diagram of the database schema, showing the tables and their relationships. ---]

*   **`students` Table**: Stores basic information about each registered student, including a unique `student_id` and their `name`.
*   **`face_embeddings` Table**: Contains the facial embeddings for each student. A single student can have multiple embeddings to improve recognition accuracy, although the current registration process averages them into a single, robust profile.
*   **`auth_logs` Table**: Records every authentication attempt, capturing the `student_id`, `timestamp`, `auth_result` (e.g., SUCCESS, FAILED_LIVENESS), `liveness_score`, and `confidence_score`.

**4.5 Face Recognition and Liveness Detection**

The system's core functionality is built on a two-stage authentication process that combines liveness detection with face recognition to ensure both the presence of a live person and their correct identity.

*   **Liveness Detection**: To prevent spoofing attacks, the system employs a hybrid liveness detection strategy:
    *   **Passive Detection**: Utilizes Local Binary Patterns (LBP) for texture analysis to distinguish between the natural texture of live skin and the artificial texture of a screen or photo.
    *   **Active Detection**: If the passive check fails, the system challenges the user to perform a natural action, such as blinking. The Eye Aspect Ratio (EAR) is calculated in real-time to verify that a genuine blink has occurred.
*   **Face Recognition**: Once liveness is confirmed, the system proceeds with face recognition:

    *   **Embedding Extraction**: The **Facenet** model is used to generate a 128-dimensional vector (embedding) that represents the unique features of the detected face.
    *   **Embedding Comparison**: This live embedding is compared against the stored embeddings in the database using **cosine similarity**. A match is only confirmed if the similarity score exceeds a strict threshold of **0.85**, which is set to minimize the risk of false positives.

**4.6 Performance Metrics and Evaluation**

To ensure the system's reliability, a comprehensive performance evaluation framework was developed (`comprehensive_performance.py`). This framework calculates a wide range of industry-standard metrics to provide a detailed assessment of the system's accuracy.

*   **Classification Metrics**:
    *   **Accuracy**: The overall correctness of the system's predictions.
    *   **Precision, Recall, and F1-Score**: Measure the balance between true positives and false positives/negatives.
*   **Biometric Error Rates**:
    *   **False Acceptance Rate (FAR)**: The likelihood of an impostor being incorrectly accepted.
    *   **False Rejection Rate (FRR)**: The likelihood of a genuine user being incorrectly rejected.
*   **Equal Error Rate (EER)**: The rate at which FAR and FRR are equal, providing a key indicator of the system's overall accuracy.

**4.7 Security and Alerting**

Security is a paramount concern in a proctoring system. In addition to the anti-spoofing measures, the system includes a real-time alerting mechanism to notify proctors of any suspicious activity.

*   **Proctor Alerting**: All critical failures, such as failed liveness checks or recognition attempts, are immediately logged to a dedicated `proctor_alerts.log` file. This file is structured for easy monitoring, allowing a proctor to see timestamped alerts with detailed information about the event, including the student ID, session ID, and the reason for the failure.
